# Spaces, Chat and the API

This page describes how Metro behaves for its users, and the HTTP API behind
it. Every human endpoint takes `Authorization: Bearer <user token>`. Errors
come back as `{"error": "..."}`.

## Identity

Your sign-in provider determines your stable ID. The
[server directory](messages.md#direct-messages-and-the-directory),
added in 0.6.0, doesn't change how IDs are assigned.

| Sign-in mode | Your `id` (stable, used for membership) | Your `actor` (display only) |
| --- | --- | --- |
| `METRO_DEV_USERS` | The username | The username |
| Local account created in the admin panel | `mu:` plus 32 hex digits, generated by the server | The display name the admin set |
| OIDC | The token's `sub` | The claim named by `METRO_OIDC_ACTOR_CLAIM` (default `sub`) |

`GET /v1/me` returns `{"id", "actor"}`. Owners add members by `id`, never by
display name. With local accounts, the admin panel lists every account's
id. In the desktop app, everyone finds theirs under **Settings → Profile →
User ID** (0.2.0 candidate). `GET /v1/me` always returns it.

**A database belongs to one identity provider.** On first start, the server
records the identity namespace it uses: dev users, or one specific OIDC
issuer. After that it refuses to start with a different one, because ids from
different providers must never be mixed. To change providers, start with a
new database (see [Upgrading](#upgrading-from-the-single-room-build)), or
restore the previous auth settings.

## Profiles

Every signed-in person has a profile: a display name, a short bio and an
avatar. It changes only how they're shown. The stable `id` never changes
and stays the only key for membership and access.

**Status.** The API below is verified by server tests
([acceptance](acceptance.md#staged-profiles-and-message-times-api-2026-11-22-project-manager-local)).
Editing your display name and picture in the desktop app (**Settings →
Profile**, with the native file picker) was verified in the 0.2.0 Linux
candidate, including after a relaunch
([acceptance](acceptance.md#staged-020-linux-candidate-local-workspace-and-desktop-qa-2026-11-22-project-manager-local)).
The live dev service's profile read endpoints were also checked.

| Request | Result |
| --- | --- |
| `GET /v1/me/profile` | `{"id", "display_name", "bio", "avatar_version"}`. `bio` and `avatar_version` are a string or `null`. |
| `PATCH /v1/me/profile` `{"display_name"?, "bio"?}` | Changes only the fields you send. `null` resets a field: the display name goes back to the one your sign-in gives. `bio` is at most 280 characters. A name that's reserved (`agent`, `runner`, `system`), looks like an id, or is someone else's id or name gets `409`. |
| `PUT /v1/me/profile/avatar` | Raw PNG or JPEG bytes, sent as `image/png` or `image/jpeg`. At most 1 MiB and 4096 pixels a side. Anything else gets `413`, `415` or `422`. |
| `GET` / `DELETE /v1/me/profile/avatar` | Your own avatar, or remove it (`204`) |
| `GET /v1/profiles/{id}` | Someone's profile |
| `GET /v1/profiles/{id}/avatar` | Someone's avatar |

- **Avatars are re-encoded.** The server decodes the upload under memory
  limits, scales it to at most 256 pixels a side, and stores and serves only
  a fresh PNG (`image/png`), with no metadata. It never fetches an image
  from a URL. `avatar_version` changes on every upload, so clients know when
  to fetch again.
- **Who can read whose profile.** In 0.5.x, you can read your own and
  those of people who share a Space with you right now. Other people
  and unknown IDs get `404`. The
  [server directory and DM profile access](messages.md#direct-messages-and-the-directory)
  added in 0.6.0 widen this.
- Avatars have no public URL. They're read with your bearer token and
  served with `Cache-Control: no-store`.
- New messages record the display name in force when they're written. Older
  history isn't rewritten. The model always sees each author's stable
  `speaker_id` next to the name.

## Spaces and members

- Anyone signed in can create a Space and becomes its **owner**. Each owner can
  have up to 50 Spaces. A new Space starts with a `lobby` room.
- Only **members** see a Space, its rooms and its threads. Members can list
  the member roster, which the desktop uses for `@` autocomplete.
- Only the **owner** adds or removes members, and chooses the Space's runner.
  Nobody can add themselves, and the owner can't be removed. Removing a member
  also stops their running agent runs in that Space.
- Only the owner renames the Space and edits its **description** (optional,
  at most 500 characters). Every member sees both.
- **Leaving.** Any member except the owner can leave. Leaving works exactly
  like being removed: their runs in the Space stop, and their own
  [library index rows](library.md) and [per-Space
  preferences](#your-preferences-in-a-space) for it are deleted. The owner
  can't leave; they can only delete the Space.
- **Deleting** is permanent and owner-only, and the owner must type the
  Space's exact name to confirm (`confirm_name`). One transaction removes
  everything in it: rooms, threads, messages and other events, reactions,
  attachment links, the Space's library files and everyone's index rows of
  them, search vectors, scheduled prompts, connection shares to the Space,
  everyone's per-Space preferences, its agents and its monitoring events.
  Its registered runner is detached, and its dedicated runner token is
  revoked, so queued and claimed jobs fail. Its running agent runs stop.
  The same transaction also permanently
  removes the Space's published Pages, their version history,
  recently deleted Pages, and Space Page drafts, including drafts that
  had not yet created a page. [Recently deleted](pages.md#deleting-pages-and-spaces)
  cannot recover them after Space deletion.
- A Space holds at most 100 members and 200 rooms, including agent-created
  threads. [Reply threads](messages.md#reply-threads) (since 0.6.0) have a
  separate limit.

| Request | Who | Result |
| --- | --- | --- |
| `GET /v1/spaces` | anyone | `{"spaces": [{"id", "name", "description", "role", "runner_paired"}]}`, only your Spaces. `description` is `""` when none was set. |
| `POST /v1/spaces` `{"name"}` | anyone | `201` with the Space, `role: "owner"` |
| `GET /v1/spaces/{sid}` | members | The Space, in the same shape |
| `PATCH /v1/spaces/{sid}` `{"name"?, "description"?}` | owner | The changed Space |
| `DELETE /v1/spaces/{sid}` `{"confirm_name"}` | owner | `204`. A name that doesn't match exactly gets `400`, and nothing is deleted. |
| `POST /v1/spaces/{sid}/leave` `{}` | members except the owner | `{"left": true, "stopped_runs": n}`. The owner gets `409`. |
| `GET /v1/spaces/{sid}/members` | members | `{"members": [{"user_id", "role"}]}` |
| `POST /v1/spaces/{sid}/members` `{"user_id"}` | owner | `201` when added, `200` if already a member |
| `DELETE /v1/spaces/{sid}/members` `{"user_id"}` | owner | `{"removed": true, "stopped_runs": n}` |
| `GET` / `POST /v1/spaces/{sid}/rooms` `{"name"}` | members | List rooms, or create one |

People outside a Space get **404**, the same as for a Space that doesn't
exist, so Metro never reveals whether a Space exists. Members who try an
owner-only action get **403**.

## Agents

A Space has one or more **agents**, at most 16. Each has:

- a **name** (up to 64 characters) and a **@handle** (up to 32 of `a-z`,
  `0-9`, `_` and `-`), unique in the Space and different from every
  member's id. Members mention it as `@handle`;
- a required one-line **description** (up to 160 characters), which the
  [classifier](#messages-and-addressing) uses to choose between agents;
- optional **instructions** (up to 4,000 characters). They're added after
  Metro's built-in instructions and can't replace or lift them;
- a **picture** (PNG or JPEG, re-encoded like a profile avatar), or its
  initial on one of eight colours;
- a **tool allowlist**: a subset of the run's tools (`workspace.list`,
  `workspace.read`, `workspace.check`, `workspace.mcp_list`,
  `workspace.mcp` and `threads`). With none,
  it can only answer. The allowlist only narrows what the run would have
  anyway: a Space without a runner still has no workspace tools, and a
  thread never gets thread tools. In the source, not released, the list
  can also hold `workspace.write` and `workspace.shell`. They're opt-in:
  `GET .../agents` lists them in `tools` but not in `default_tools`, so
  existing agents and agents created without `tools` don't get them. Shell
  commands also follow the runner's
  [shell policy](runner.md#shell-commands-in-the-source-not-released).

Exactly one agent is the Space's **default**. Every Space starts with one
default agent, named *Metro*, with the handle `agent` and the default tools; Spaces
created before agents existed get the same one, so they behave as before.
`agent` is reserved: only that agent may keep it, and the generic `@agent`
always means "the default agent, or the one the classifier picks" (below).

- Only the owner creates, edits and deletes agents, sets pictures and picks
  the default. Members read everything, instructions included. Outsiders
  get `404`, and members who try to change an agent get `403`.
- The last agent can't be deleted. Deleting the default makes the oldest
  remaining agent the default.
- Each run records its agent, and every event of the run carries it
  (`activity.agent`: id, handle, name, picture version and colour). Its
  `started` marker also says how the agent was chosen (`activity.pick`, for
  example *Addressed: @coder*, *Default agent* or *Picked by classifier:
  Coder*). Since 0.6.1, a run the classifier picked has no
  `activity.pick`: it shows only as that agent's run, and a weak pick that
  fell back says only *Default agent*.
- Threads an agent's run creates keep that agent.
- [Scheduled prompts](schedules.md) in a Space use its default agent.

| Request | Who | Result |
| --- | --- | --- |
| `GET /v1/spaces/{sid}/agents` | members | `{"agents": [...], "tools": [...]}`, the default first. `tools` lists every allowlist entry. |
| `POST /v1/spaces/{sid}/agents` `{"name", "handle", "description", "instructions"?, "tools"?, "color"?, "is_default"?}` | owner | `201` with the agent. Without `tools`, it gets `default_tools`. |
| `GET` / `PATCH` / `DELETE /v1/spaces/{sid}/agents/{aid}` | members read, owner changes | `PATCH` takes the same fields. `is_default` can only be set to `true`. A taken handle, `agent` for another agent, a 17th agent or deleting the last one gets `409`. |
| `GET` / `PUT` / `DELETE /v1/spaces/{sid}/agents/{aid}/avatar` | members read, owner changes | The picture, read with your bearer token only and never cached |

## Your preferences in a Space

Each member has their own preferences in each Space
(`GET` / `PUT /v1/spaces/{sid}/prefs`). Only they read or write them, and
leaving or being removed deletes them.

| Field | Meaning |
| --- | --- |
| `classify_unaddressed` | Let your System One connection decide whether your unaddressed messages here are for one of the Space's agents, and which. Off by default. It can be turned on only while you have a System One connection usable in this Space (otherwise `409`); `classifier_available` in the answer says whether you do. See [system-one.md](system-one.md#opt-in-classification-of-unaddressed-messages). |
| `default_model` | `{"provider_connection_id", "model_id"?, "reasoning_effort"?}`: your chat model for every agent here |
| `agent_models` | Per agent id, your chat model for that agent here |
| `routing` | Whether your [use-case routing](system-one.md#use-case-routing), if you turned it on, applies here. Default on. |

Every model you pick must be a chat connection you can use in this Space:
your own, or one shared with this Space or the organization. It's checked
when you save and again on every run. The order a run's model is chosen in
is in [settings.md](settings.md#which-model-a-run-uses).

Open [Space settings](released-0.5.0.md#space-settings) from the room
header or sidebar menu. Metro 0.5.0 groups **General**, **Members**,
**Runner**, **Agents**, and **Your preferences** in one window.

## Messages and addressing

See [desktop mentions](released-0.5.0.md#mentions-in-rooms-and-threads),
[private sender notices](released-0.5.0.md#private-sender-notices), and the
[Space send protocol](released-0.5.0.md#space-send-protocol-client-developers)
for the 0.5.0 composer and API.

The table and rules below describe 0.5.0. **Since 0.6.0,**
[replying to an agent](messages.md#reply) adds an explicit recipient, and
the [opt-in classifier](system-one.md#classification-since-060)
uses a lower threshold and brief room context for unaddressed text.
**Since 0.6.1,** a message is stored and shown before
[System One decides](system-one.md#decisions-after-posting), and members
can [delete messages](messages.md#delete).

| You write | Addressed to | Which agent runs |
| --- | --- | --- |
| `Can someone review this?` | the room | none (unless you [opted in](#your-preferences-in-a-space), below) |
| `@bob can you review this?` | Bob | none, ever |
| `@coder fix the build` | the agent `@coder` | `@coder` |
| `@coder @writer draft and check this` | both agents | one run each |
| `@agent summarize today` | the generic agent | the default agent, or the classifier's pick |
| `@bob @agent check greet.sh` | Bob and the generic agent | as for `@agent` |
| any text sent with **Ask agent** | the generic agent, or the agent you picked | as for `@agent`, or that agent |

Explicit recipients always decide who a message is addressed to:

- **People only** (`@bob`, no agent, not sent with Ask agent) never starts
  an agent and is never sent to System One.
- **An agent's `@handle`** (or Ask agent with that agent chosen) starts that
  agent, with no classification. Several agents mentioned start one run
  each; one agent mentioned twice still runs once.
- **`@agent` or Ask agent without an agent** starts the default agent. If
  the sender [opted in](#your-preferences-in-a-space) to classification in
  this Space (which needs a usable System One connection) and the Space has
  more than one agent, one System One Choice over the agents (with no "no
  agent" option) picks one instead, on the sender's System One connection.
  An unsure answer keeps the default agent. If the decision fails (the
  connection errs, times out, answers malformed or can no longer be used),
  the room shows an error and no agent runs for `@agent`.
- **Unaddressed** text is ordinary conversation, unless the sender opted in
  here. Then one System One Choice over the agents plus *No agent* decides;
  only a clear pick starts that agent, as the sender. *No agent*, an unsure,
  malformed or failed answer starts nothing. See
  [system-one.md](system-one.md#opt-in-classification-of-unaddressed-messages).

A [scheduled prompt](schedules.md) counts as its creator asking the Space's
default agent, with no classification. In legacy text inference, `@agent`, `@<agent handle>`
and `@<member id>` count only as standalone handles, and `@<member id>` only
for current members of the Space. The agent's history shows each message's
author and recipients, so it can tell a question for Bob from one for itself.

- `POST /v1/spaces/{sid}/rooms/{rid}/messages`
  `{"text", "invoke_agent"?, "agent_id"?, "mentions"?}` returns `202` with
  the event. `agent_id` goes with `invoke_agent` to ask one agent instead of
  the generic one. `mentions` is a list of up to 32 recipients, each
  `{"kind":"agent"}` (the generic `@agent`),
  `{"kind":"agent","agent_id":"ag-…"}` (one agent) or
  `{"kind":"user","id":"<member id>"}`. The desktop picker sends these, which
  also works for opaque OIDC ids that nobody would type.
  Since 0.3.2, a message to the agent
  may also carry `provider_connection_id`, `model_id` and
  `reasoning_effort` to choose the model and thinking level for that turn,
  and `asset_ids` to attach Library files. See
  [settings.md](settings.md#which-model-a-run-uses).
- `GET /v1/spaces/{sid}/rooms/{rid}/events?after=<id>` returns
  `{"events": [...]}`. Message events carry `mentions` and an `audience`:
  `room`, `agent`, `users` or `mixed`. A `reasoning_summary` event holds the
  reasoning summary a provider returned for one model turn of a run (for
  example ChatGPT's, through a device connection), as the provider sent it,
  at most 4,000 characters, tagged with the run's activity. It's never a
  message, never part of the model's history and never indexed for search.
  Metro never writes one of its own, and redacted reasoning is skipped.
- `POST /v1/spaces/{sid}/rooms/{rid}/demo` `{}` runs `workspace.list` on the
  Space's runner and never calls a model. It returns `409` if the Space has no
  paired runner.

## Message times

**Status.** Verified at the API and in model context with scripted providers
([acceptance](acceptance.md#staged-profiles-and-message-times-api-2026-11-22-project-manager-local)).
The desktop app shows each message's time, in your local time zone, and a
day divider. The conversion is verified by tests with `Intl` time zones, and
the 0.2.0 Linux candidate showed the times. The live
dev service's timestamp reads were checked too.

- **Events carry `created_at`.** Every event returned over HTTP, in rooms,
  threads and personal Chat, has `created_at`: the time the server stored
  it, as RFC 3339 UTC with milliseconds (for example
  `2026-11-22T03:04:05.123Z`), or `null` when the server has no usable
  recorded time, such as some older history. The field is additive.
- **Every event has it**, the agent's own replies included.
- **Only the server sets it.** It can't be sent with a message, it doesn't
  change once it's written, and a missing time is never filled in with
  "now". Events are still ordered by `id`, not by time.
- **What the model receives.** Each user-side message in the agent's
  context, current and earlier, carries Metro context with `sent_at`: the
  same UTC time, or `null`. So does a child thread's task from its parent.
  The agent's own earlier replies stay plain assistant text, with no
  `sent_at`. Each run also states the server's UTC time when that run
  started, not a live clock. Times or dates written
  inside a message's text are treated as text, not as Metro's record. This
  applies in Chat, rooms, threads and scheduled prompts, and to server-side
  and device connections alike.

## Reactions

Anyone who can see a message can react with one of 👍 👀 ✅ 🙏 ❤️ 🎉. This
works on human and agent messages in Chat, rooms and threads.

- `PUT .../events/{eid}/reactions` `{"emoji"}` adds your reaction, and
  `DELETE` with the same body removes it. Both return `{"changed": bool}`.
  Repeating a reaction you already made, or removing one you didn't make,
  changes nothing and records nothing.
- The path prefix is `/v1/spaces/{sid}/rooms/{rid}` for rooms and threads, and
  `/v1/chat` for Chat.
- **Reactions never start agent work**, and they never mean a task is
  complete. A conversation between people stays between people, reactions
  included.
- When the agent is addressed, it may answer with a single reaction instead of
  a redundant reply, for example acknowledging a thank-you.

## Space agent behaviour

**Since 0.6.0,** a Space agent's built-in prompt asks it
to answer usefully (in Markdown when helpful), acknowledge with a reaction
if enough, or send no reply if it would interrupt people. The prompt
discourages silence when a person names the agent or replies to it with
a question or request. An empty final answer or `METRO_NO_REPLY` completes
the run without an agent message; a reaction followed by
`METRO_REACTION_ONLY` can acknowledge a message without a text reply.
The completed activity metadata distinguishes replies, reactions and no
reply. Since 0.6.1, the desktop shows nothing in the
transcript for a run that ends without an agent message.

New Spaces get a default agent instructed to help the whole room,
suggest a better-suited agent by handle when appropriate, and ask a
short question rather than guess. Existing agents keep their stored
instructions. Owner instructions add to, not replace, Metro's prompt.

Room runs get a bounded **Space context** block (up to 8 KiB): Space
name and description, room or thread, applicable parent and anchor
information, current members' display names, stable IDs and roles (up
to 50 members), and the agent roster. This goes to the run's model;
names and descriptions written by people are context, not instructions.
Personal Chat doesn't get this block.

## Threads

A room's agent can delegate work to **child threads** with the tools
`thread_create`, `thread_send`, `thread_status` and `thread_stop`.

- A thread is a child room with its own persistent transcript. The desktop
  shows it under its parent room (`parent_room_id`), with a link back.
- A thread inherits its Space's members and paired runner, and keeps the
  agent and the model connection of the run that created it. Its results
  are posted back to the parent room as `thread` events.
- Only an agent whose allowlist includes `threads` gets the thread tools.
- Threads go only one level deep: a thread can't create threads. A room can
  have at most 16 of them.

**Since 0.6.0,** [reply threads](messages.md#reply)
are anchored to a room message. They include the anchor in agent
history and don't mirror answers into the parent room. If an
agent-created thread completes without a reply, its parent still gets a
completion note.

## Personal Chat

- Every user has a private Chat with the agent. Only that user can see it, and
  it works with zero Spaces.
- **Send** asks your agent directly, even with attachments only. **Save
  note** keeps the message without starting a run. Attachments go into
  your personal Library, not to the Chat agent. See [Personal Chat](released-0.5.0.md#personal-chat)
  for `POST /v1/chat/messages` and compatibility behavior.
  Read the transcript with `GET /v1/chat/events?after=<id>`.
- The Chat agent can acknowledge a message with `react_to_message`.
  Web tools require a separate [opt-in](web-search.md). Chat never uses a
  runner directly and has no workspace or agent-thread management tools.
  In 0.5.x it cannot read Space transcripts or post in Spaces.
  **Since 0.6.0,** [Metro in Chat](released-0.6.0.md#metro-in-chat)
  can read and post as you after its notice gate, and you can
  [forward](messages.md#forward) a message yourself.
- The manual cross-Space controls in Chat are separate. **Agent runs**
  lists only Space runs, including threads; you can open, follow up on or
  stop runs where permitted (see [Runs](#runs)).
  [New task and Follow up](released-0.5.0.md#recipient-safe-dispatch-and-exact-destination-follow-up)
  send once to the generic agent in a verified room or thread. To send
  later or repeatedly, use **Scheduled tasks › New task**
  ([schedules.md](schedules.md)). All of these check your membership.

## Runs

- `GET /v1/runs` returns `{"runs": [...]}`: agent runs in Spaces you belong
  to, threads included. Personal Chat runs aren't listed. A run's status is
  `running`, `completed`, `failed` or `cancelled`.
- `POST /v1/runs/{id}/stop` `{}` stops a run and returns it as `cancelled`.
  The person who started a run can stop it, and so can the Space's owner.
  Other members get 403, outsiders get 404, and a run that has already
  finished gets 409.
- Stopping halts the agent's orchestration. A tool job that a runner has
  already claimed may keep running on that machine until it ends or times
  out. In the source, not released, a running `workspace.shell` command is
  killed within a few seconds of the stop, and a pending shell approval is
  cancelled.
- In the source, not released, shell approvals are run activity in the
  room or thread (`shell_approval`, `shell_approval_resolved`), never
  messages, agent history or search results. See
  [Approvals](runner.md#approvals).
- Run history is kept in memory, bounded, and lost on restart. Room
  transcripts are durable.
- **Since 0.6.0,** the initiator can
  [retry eligible runs](released-0.6.0.md#new-api-routes-and-fields);
  personal Chat has a separate turn stop endpoint and remains out of
  the runs list.
- At most 4 agent runs are active per Space, and 8 per server.

## Monitoring events

**Status.** Released in 0.3.2 (`797eac1`, with the personal
scope added in `c5e2753`), covered by the server's automated tests
(`crates/server/tests/monitoring.rs`), and checked through the desktop's
**Settings → Monitoring** in the native GTK app on Debian 13 in the local
[57409bb setup cut](acceptance.md#staged-installers-and-setup-at-57409bb-2026-11-23-project-manager-local).

The server keeps a short log of things that went wrong, so a Space's owner,
a person, or an operator can see that something failed without anyone
sharing logs. A read names exactly one scope; nothing combines them.

- `GET /v1/monitoring/events?scope=me` returns **your own** personal Chat
  events: your Chat turns that failed or were refused, and problems with the
  model connection they used. The owner is the signed-in person, taken from
  authentication only. Nobody else can read them, **org admins included**.
- `GET /v1/monitoring/events?space_id=SID` returns `{"events": [...]}` for
  one Space: failed, timed-out or refused agent runs, problems with the
  model connection a run used (unreachable, credentials rejected, rate
  limited, server error, unusable reply), and runner problems (queue full,
  no runner picked up the job, no result in time, runner changed). When
  no runner picks up a job, the room says which case it is: the Space
  has no runner; its runner isn't connected (it hasn't checked in since
  the server started, or last checked in some minutes ago); or the
  runner is connected but didn't pick up the job in time. Only the
  Space's **current owner** may read it. Members get 403, and outsiders and
  unknown ids get 404, checked on every request.
- `GET /v1/monitoring/events` with no `space_id` returns the server's own
  events (started, scheduler failures). Only
  [organization admins](deploy.md) may read it; everyone else gets 403.
- Each event is only its scope, a time, a component, a fixed code and that
  code's fixed one-line summary. A personal event's scope is its owner's
  stable user id; nothing else about a person is stored. No message text,
  prompt, error text from a vendor or device, path, URL or token is ever
  stored. Personal and Space events never appear in the server-wide log.
  (The first version, `797eac1`, recorded no personal Chat events at all.)
- Events are kept for 30 days and at most 500 per scope, across restarts.
  A read returns the newest 100.
- Summaries are deliberately coarse, such as *The model service rejected
  the connection's credentials.* Details of a failed Sign in with ChatGPT
  call stay on the device that made it ([desktop
  README](../apps/desktop/README.md#troubleshooting)).

## Runner pairing

In Metro 0.5.0, use [Space settings → Runner and the guarded assignment
API](released-0.5.0.md#guarded-runner-changes). The unguarded write
routes below are for older clients, not a fallback for a failed guarded
request.

A Space uses **at most one runner**, and only its owner chooses it. There are
two kinds, described fully in [runners.md](runners.md):

- **Dedicated token.** The owner issues the Space's runner token with
  `POST /v1/spaces/{sid}/runner-token` `{}`, which returns `{"token"}` with
  `Cache-Control: no-store`. The server keeps only a hash, so the token can't
  be shown again. Issuing a new token **rotates** it: the old token stops
  working, and jobs claimed with it fail. `DELETE` revokes the token (`204`).
  That token serves this Space only: every room and thread in it, and nothing
  else.
- **Registered runner.** The owner attaches one of the runners they're
  allowed to use (their own personal runners, or any organization runner)
  with `PUT /v1/spaces/{sid}/runner` `{"runner_id"}`, and detaches it with
  `DELETE /v1/spaces/{sid}/runner`. The same runner can serve other Spaces
  too, each in its own directory on the runner.

A Space can't have both. Issuing a dedicated token while a registered runner
is attached, or attaching one while a dedicated token exists, returns `409`.
`DELETE /v1/spaces/{sid}/runner` clears whichever one the Space has.
`GET /v1/spaces/{sid}/runner` shows members which runner the Space uses (its
name, scope and kind), never a credential.

- `runner_paired` means the Space has a dedicated token or an attached
  runner. It doesn't mean a runner is online.
- Removing or replacing the assignment drops queued and claimed jobs.
  Rotation invalidates claimed work; unclaimed work can remain queued
  for the same runner.
- Without a runner, a Space still works for chat and Ask agent; only the
  workspace tools are missing. Every member can trigger the runner's tools,
  so every member can read the Space's workspace on it. In the source, not
  released, an agent with `workspace.write` lets every member change files
  there, and `workspace.shell` lets them ask for commands that run as the
  runner's user, subject to the
  [shell policy](runner.md#shell-commands-in-the-source-not-released). See
  [deploy.md](deploy.md#trust-boundaries).

## Keeping secrets out of screenshots and logs

User tokens, runner tokens and model keys are all bearer secrets.

- Keep tokens in mode-600 files. Don't `echo` them or paste them into chat.
  The README's commands never print one.
- The desktop app holds your token in memory only. It shows a new runner token
  once and clears it when you hide it, leave the view or disconnect. Hide it
  before you screen-share.
- Tokens passed with `curl -H` are briefly visible to other local users in the
  process list. On a shared machine, use `curl --header @file` instead.
- If a token leaks, rotate it: issue a new runner token, or change the dev
  token and restart. For OIDC tokens, rely on your provider's controls and
  short lifetimes.

## Upgrading a Spaces database

A database from the first Spaces build upgrades in place on startup. Its
Spaces, members, rooms and dedicated runner tokens are kept, and each paired
Space keeps its dedicated runner. Registered runners start out empty. No
Space is attached to one until its owner chooses. Back up the volume first
anyway.

## Upgrading from the single-room build

The single-room build's rooms belong to no Space. Metro never assigns them to
anyone. If the database holds any of that history, the server refuses to
start and says how many rooms and events it found. It accepts an old database
only if that database holds nothing but an empty default lobby.

To upgrade with Compose without losing that history:

1. Stop the server, then copy the database out as your backup:

   ```sh
   docker compose stop server
   docker compose cp server:/data/. ./metro-single-room-backup/
   ```

2. Start the new version on a **new volume** and leave the old one untouched.
   Add a project name to `.env`, for example
   `COMPOSE_PROJECT_NAME=metro-spaces`, then run `docker compose up -d`.
   Compose creates `metro-spaces_server-data`; the old volume stays as it was.
3. Recreate your Spaces and members, and issue new runner tokens.

Outside Compose, point `METRO_DB` at a new, empty file and keep the old one.
