# Spaces, Chat and the API

This page describes how Metro behaves for its users, and the HTTP API behind
it. Every human endpoint takes `Authorization: Bearer <user token>`. Errors
come back as `{"error": "..."}`.

## Identity

Your identity provider decides who you are. Metro keeps no user directory.

| Sign-in mode | Your `id` (stable, used for membership) | Your `actor` (display only) |
| --- | --- | --- |
| `METRO_DEV_USERS` | The username | The username |
| Local account created in the admin panel | `mu:` plus 32 hex digits, generated by the server | The display name the admin set |
| OIDC | The token's `sub` | The claim named by `METRO_OIDC_ACTOR_CLAIM` (default `sub`) |

`GET /v1/me` returns `{"id", "actor"}`. Owners add members by `id`, never by
display name. With local accounts, the admin panel lists every account's
id. In the desktop app, everyone finds theirs under **Settings → Profile →
User ID** (0.2.0 candidate). `GET /v1/me` always returns it.

**A database belongs to one identity provider.** On first start, the server
records the identity namespace it uses: dev users, or one specific OIDC
issuer. After that it refuses to start with a different one, because ids from
different providers must never be mixed. To change providers, start with a
new database (see [Upgrading](#upgrading-from-the-single-room-build)), or
restore the previous auth settings.

## Profiles

Every signed-in person has a profile: a display name, a short bio and an
avatar. It changes only how they're shown. The stable `id` never changes
and stays the only key for membership and access.

**Status.** The API below is verified by server tests
([acceptance](acceptance.md#staged-profiles-and-message-times-api-2026-11-22-project-manager-local)).
Editing your display name and picture in the desktop app (**Settings →
Profile**, with the native file picker) was verified in the 0.2.0 Linux
candidate, including after a relaunch
([acceptance](acceptance.md#staged-020-linux-candidate-local-workspace-and-desktop-qa-2026-11-22-project-manager-local)).
The live dev service's profile read endpoints were also checked.

| Request | Result |
| --- | --- |
| `GET /v1/me/profile` | `{"id", "display_name", "bio", "avatar_version"}`. `bio` and `avatar_version` are a string or `null`. |
| `PATCH /v1/me/profile` `{"display_name"?, "bio"?}` | Changes only the fields you send. `null` resets a field: the display name goes back to the one your sign-in gives. `bio` is at most 280 characters. A name that's reserved (`agent`, `runner`, `system`), looks like an id, or is someone else's id or name gets `409`. |
| `PUT /v1/me/profile/avatar` | Raw PNG or JPEG bytes, sent as `image/png` or `image/jpeg`. At most 1 MiB and 4096 pixels a side. Anything else gets `413`, `415` or `422`. |
| `GET` / `DELETE /v1/me/profile/avatar` | Your own avatar, or remove it (`204`) |
| `GET /v1/profiles/{id}` | Someone's profile |
| `GET /v1/profiles/{id}/avatar` | Someone's avatar |

- **Avatars are re-encoded.** The server decodes the upload under memory
  limits, scales it to at most 256 pixels a side, and stores and serves only
  a fresh PNG (`image/png`), with no metadata. It never fetches an image
  from a URL. `avatar_version` changes on every upload, so clients know when
  to fetch again.
- **Who can read whose profile.** You can read your own, and those of people
  who share a Space with you right now. It's checked on every request.
  Anyone else, and unknown ids, get `404`. There's no directory, and no
  admin bypass.
- Avatars have no public URL. They're read with your bearer token and
  served with `Cache-Control: no-store`.
- New messages record the display name in force when they're written. Older
  history isn't rewritten. The model always sees each author's stable
  `speaker_id` next to the name.

## Spaces and members

- Anyone signed in can create a Space and becomes its **owner**. Each owner can
  have up to 50 Spaces. A new Space starts with a `lobby` room.
- Only **members** see a Space, its rooms and its threads. Members can list
  the member roster, which the desktop uses for `@` autocomplete.
- Only the **owner** adds or removes members, and chooses the Space's runner.
  Nobody can add themselves, and the owner can't be removed. Removing a member
  also stops their running agent runs in that Space.
- A Space holds at most 100 members and 200 rooms, threads included.

| Request | Who | Result |
| --- | --- | --- |
| `GET /v1/spaces` | anyone | `{"spaces": [{"id", "name", "role", "runner_paired"}]}`, only your Spaces |
| `POST /v1/spaces` `{"name"}` | anyone | `201` with the Space, `role: "owner"` |
| `GET /v1/spaces/{sid}/members` | members | `{"members": [{"user_id", "role"}]}` |
| `POST /v1/spaces/{sid}/members` `{"user_id"}` | owner | `201` when added, `200` if already a member |
| `DELETE /v1/spaces/{sid}/members` `{"user_id"}` | owner | `{"removed": true, "stopped_runs": n}` |
| `GET` / `POST /v1/spaces/{sid}/rooms` `{"name"}` | members | List rooms, or create one |

People outside a Space get **404**, the same as for a Space that doesn't
exist, so Metro never reveals whether a Space exists. Members who try an
owner-only action get **403**.

## Messages and addressing

| You write | Addressed to | Agent starts? |
| --- | --- | --- |
| `Can someone review this?` | the room | no |
| `@bob can you review this?` | Bob | no |
| `@agent summarize today` | the agent | yes |
| `@bob @agent check greet.sh` | Bob and the agent | yes |
| any text sent with **Ask agent** | the agent | yes |

Mentioning a person never starts agent work. Only `@agent` or Ask agent does.
That's the default. A [scheduled prompt](schedules.md) counts as its owner
writing `@agent`.
A person can also opt in to having System One judge their own unaddressed
messages ([system-one.md](system-one.md#opt-in-classification-of-unaddressed-messages)).
It's off by default, and it only ever judges messages with no mention that
weren't sent with Ask agent. Explicit recipients always decide who a message is
addressed to. In text, `@agent` and `@<member id>` count only as standalone handles, and
`@<member id>` only for current members of the Space. The agent's history shows each message's
author and recipients, so it can tell a question for Bob from one for itself.

- `POST /v1/spaces/{sid}/rooms/{rid}/messages`
  `{"text", "invoke_agent"?, "mentions"?}` returns `202` with the event.
  `mentions` is a list of up to 32 recipients, each `{"kind":"agent"}` or
  `{"kind":"user","id":"<member id>"}`. The desktop picker sends these, which
  also works for opaque OIDC ids that nobody would type.
- `GET /v1/spaces/{sid}/rooms/{rid}/events?after=<id>` returns
  `{"events": [...]}`. Message events carry `mentions` and an `audience`:
  `room`, `agent`, `users` or `mixed`.
- `POST /v1/spaces/{sid}/rooms/{rid}/demo` `{}` runs `workspace.list` on the
  Space's runner and never calls a model. It returns `409` if the Space has no
  paired runner.

## Message times

**Status.** Verified at the API and in model context with scripted providers
([acceptance](acceptance.md#staged-profiles-and-message-times-api-2026-11-22-project-manager-local)).
The desktop app shows each message's time, in your local time zone, and a
day divider. The conversion is verified by tests with `Intl` time zones, and
the 0.2.0 Linux candidate showed the times. The live
dev service's timestamp reads were checked too.

- **Events carry `created_at`.** Every event returned over HTTP, in rooms,
  threads and personal Chat, has `created_at`: the time the server stored
  it, as RFC 3339 UTC with milliseconds (for example
  `2026-11-22T03:04:05.123Z`), or `null` when the server has no usable
  recorded time, such as some older history. The field is additive.
- **Every event has it**, the agent's own replies included.
- **Only the server sets it.** It can't be sent with a message, it doesn't
  change once it's written, and a missing time is never filled in with
  "now". Events are still ordered by `id`, not by time.
- **What the model receives.** Each user-side message in the agent's
  context, current and earlier, carries Metro context with `sent_at`: the
  same UTC time, or `null`. So does a child thread's task from its parent.
  The agent's own earlier replies stay plain assistant text, with no
  `sent_at`. Each run also states the server's UTC time when that run
  started, not a live clock. Times or dates written
  inside a message's text are treated as text, not as Metro's record. This
  applies in Chat, rooms, threads and scheduled prompts, and to server-side
  and device connections alike.

## Reactions

Anyone who can see a message can react with one of 👍 👀 ✅ 🙏 ❤️ 🎉. This
works on human and agent messages in Chat, rooms and threads.

- `PUT .../events/{eid}/reactions` `{"emoji"}` adds your reaction, and
  `DELETE` with the same body removes it. Both return `{"changed": bool}`.
  Repeating a reaction you already made, or removing one you didn't make,
  changes nothing and records nothing.
- The path prefix is `/v1/spaces/{sid}/rooms/{rid}` for rooms and threads, and
  `/v1/chat` for Chat.
- **Reactions never start agent work**, and they never mean a task is
  complete. A conversation between people stays between people, reactions
  included.
- When the agent is addressed, it may answer with a single reaction instead of
  a redundant reply, for example acknowledging a thank-you.

## Threads

A room's agent can delegate work to **child threads** with the tools
`thread_create`, `thread_send`, `thread_status` and `thread_stop`.

- A thread is a child room with its own persistent transcript. The desktop
  shows it under its parent room (`parent_room_id`), with a link back.
- A thread inherits its Space's members and paired runner. Its results are
  posted back to the parent room as `thread` events.
- Threads go only one level deep: a thread can't create threads. A room can
  have at most 16 of them.

## Personal Chat

- Every user has a private Chat with the agent. Only that user can see it, and
  it works with zero Spaces.
- `GET /v1/chat/events?after=<id>` and `POST /v1/chat/messages`
  `{"text", "invoke_agent"?, "provider_connection_id"?}` work like room
  messages. `provider_connection_id` picks one of your own model connections
  for that reply only. It's allowed only on a message to the agent, and
  someone else's connection, or one that doesn't exist, gets `404`. See
  [settings.md](settings.md#which-model-a-run-uses). Chat has no other
  members, so only `@agent` or `invoke_agent` addresses anyone.
- The Chat agent's only tool is `react_to_message`, which acknowledges a
  message addressed to it in your Chat. It has no runner, workspace or thread
  tools, and it can't read Space transcripts. Chat never uses a runner, not
  even your personal registered one, and Chat messages are never forwarded
  into a Space.
- The cross-Space controls in Chat are for you, not the agent: you can list,
  open, follow up on and stop runs (see [Runs](#runs)). In the desktop app,
  **New task** beside Chat's agent runs sends a task right away to the agent
  of a Space and a room or thread you pick explicitly. It shows the
  recipient (*To: agent in Acme › #lobby*) before **Send to agent**, and
  **Follow up** on a run opens the same form. It sends once, now. To send
  later or repeatedly, use **Scheduled tasks › New task**
  ([schedules.md](schedules.md)). All of these check your membership.

## Runs

- `GET /v1/runs` returns `{"runs": [...]}`: agent runs in Spaces you belong
  to, threads included. Personal Chat runs aren't listed. A run's status is
  `running`, `completed`, `failed` or `cancelled`.
- `POST /v1/runs/{id}/stop` `{}` stops a run and returns it as `cancelled`.
  The person who started a run can stop it, and so can the Space's owner.
  Other members get 403, outsiders get 404, and a run that has already
  finished gets 409.
- Stopping halts the agent's orchestration. A tool job that a runner has
  already claimed may keep running on that machine until it ends or times
  out.
- Run history is kept in memory, bounded, and lost on restart. Room
  transcripts are durable.
- At most 4 agent runs are active per Space, and 8 per server.

## Runner pairing

A Space uses **at most one runner**, and only its owner chooses it. There are
two kinds, described fully in [runners.md](runners.md):

- **Dedicated token.** The owner issues the Space's runner token with
  `POST /v1/spaces/{sid}/runner-token` `{}`, which returns `{"token"}` with
  `Cache-Control: no-store`. The server keeps only a hash, so the token can't
  be shown again. Issuing a new token **rotates** it: the old token stops
  working, and jobs claimed with it fail. `DELETE` revokes the token (`204`).
  That token serves this Space only: every room and thread in it, and nothing
  else.
- **Registered runner.** The owner attaches one of the runners they're
  allowed to use (their own personal runners, or any organization runner)
  with `PUT /v1/spaces/{sid}/runner` `{"runner_id"}`, and detaches it with
  `DELETE /v1/spaces/{sid}/runner`. The same runner can serve other Spaces
  too, each in its own directory on the runner.

A Space can't have both. Issuing a dedicated token while a registered runner
is attached, or attaching one while a dedicated token exists, returns `409`.
`DELETE /v1/spaces/{sid}/runner` clears whichever one the Space has.
`GET /v1/spaces/{sid}/runner` shows members which runner the Space uses (its
name, scope and kind), never a credential.

- `runner_paired` means the Space has a dedicated token or an attached
  runner. It doesn't mean a runner is online.
- Changing the Space's runner in any way makes its queued and claimed jobs
  fail. They never move to the new runner.
- Without a runner, a Space still works for chat and Ask agent; only the
  workspace tools are missing. Every member can trigger the runner's tools,
  so every member can read the Space's workspace on it. See
  [deploy.md](deploy.md#trust-boundaries).

## Keeping secrets out of screenshots and logs

User tokens, runner tokens and model keys are all bearer secrets.

- Keep tokens in mode-600 files. Don't `echo` them or paste them into chat.
  The README's commands never print one.
- The desktop app holds your token in memory only. It shows a new runner token
  once and clears it when you hide it, leave the view or disconnect. Hide it
  before you screen-share.
- Tokens passed with `curl -H` are briefly visible to other local users in the
  process list. On a shared machine, use `curl --header @file` instead.
- If a token leaks, rotate it: issue a new runner token, or change the dev
  token and restart. For OIDC tokens, rely on your provider's controls and
  short lifetimes.

## Upgrading a Spaces database

A database from the first Spaces build upgrades in place on startup. Its
Spaces, members, rooms and dedicated runner tokens are kept, and each paired
Space keeps its dedicated runner. Registered runners start out empty. No
Space is attached to one until its owner chooses. Back up the volume first
anyway.

## Upgrading from the single-room build

The single-room build's rooms belong to no Space. Metro never assigns them to
anyone. If the database holds any of that history, the server refuses to
start and says how many rooms and events it found. It accepts an old database
only if that database holds nothing but an empty default lobby.

To upgrade with Compose without losing that history:

1. Stop the server, then copy the database out as your backup:

   ```sh
   docker compose stop server
   docker compose cp server:/data/. ./metro-single-room-backup/
   ```

2. Start the new version on a **new volume** and leave the old one untouched.
   Add a project name to `.env`, for example
   `COMPOSE_PROJECT_NAME=metro-spaces`, then run `docker compose up -d`.
   Compose creates `metro-spaces_server-data`; the old volume stays as it was.
3. Recreate your Spaces and members, and issue new runner tokens.

Outside Compose, point `METRO_DB` at a new, empty file and keep the old one.
